1 文件目的與目前狀態
1.1 本文件供接手的人工智慧理解使用者的問題、比較候選方案並接續選型。使用者目前要求整理方案，尚未要求實作整套系統。
1.2 已完成英文來源研究與架構比較；尚未讀取實際資料庫、驗證文件數量、安裝工具、建立索引或實測效益。以下區分使用者已知需求、建議與未知資訊，勿將建議視為已部署事實。
1.3 目前建議的起步方式是「搜尋索引＋原文回查」，要求全面整理時再加「檔案清單＋逐批成果＋持久進度」。全庫摘要、GraphRAG、RAPTOR 暫不列為起步必要條件。

2 使用者情境
2.1 資料範圍由使用者描述為 `/g/data/tv26101718708/*.md`，文件超過一萬份；數量未實測，是否包含子目錄尚未確認。
2.2 使用者預期透過類似 AI CLI agent 的工具，與人工智慧互動對話，請它找資料、比較內容、整理與歸納。尚未指定實際 CLI、模型或服務商。
2.3 「找好的方法」「列出很多方法」「收斂成主要方法」是未來使用方式的例子，不是限定資料內容或唯一任務。預處理不應只保留方法類資訊，或預設所有未來問題。
2.4 使用者在意模型的上下文與注意力限制：資料量大時，模型可能只處理部分內容、忽略先前資訊，或過早交出看似完成的答案。
2.5 使用者希望事前處理資料，或使用務實提示詞，使日後的互動在有限上下文下更有效、更接近需求；也希望知道哪些方案互補、哪些重複，應保留哪些。
2.6 尚未確認日常快速查找與全面盤點的使用比例，也未確認可接受的前置時間、模型費用與維護成本。「兩者都需要，先從低成本開始」目前只是選型假設。

3 真正要解決的問題
3.1 搜尋完整性：模型找到幾個合理答案，不能證明其已比較全部相關材料。少量候選搜尋結果可能掩蓋大量未被找到的資料。
3.2 歸納完整性：將大量內容收斂成少數主題時，可能合併不該合併的差異，遺漏少見觀點、適用條件、反例或矛盾。
3.3 工作可核對性：使用者難以知道哪些文件或段落已處理、哪些未處理，以及回答到底依據哪些原文。
3.4 工作連續性：長任務不應只依賴對話記憶；上下文壓縮或更換對話後，仍應能找到既有成果與未完成位置。
3.5 不可誇大前提：「同一個對話必然失敗」並未成立。應將對話視為操作介面，讓索引、成果與進度存於外部，每次只載入當下需要的內容。
3.6 重要區分：處理清單可以核對遍歷範圍；全部項目標為完成，不代表模型理解毫無遺漏，也不代表找齊所有語意相關資訊。

4 最小需求
4.1 保留原文作為資料主體，索引、摘要與主題目錄都應能回到來源。摘要用途是導航或輔助整合，不能取代原文證據。
4.2 支援兩種操作模式：日常查找以取得相關候選資料為目標；全面整理則以明確範圍內的逐批處理為目標。兩者不可混稱。
4.3 回答須能交代來源位置及支持內容；跨文件合併時保留重要條件、差異、例外與矛盾。
4.4 全面整理須保存處理清單、逐來源成果、失敗與未完成範圍，以便接續及重新彙整。長文件需細分處理單位，避免讀取部分內容便算整份完成。
4.5 每次送入模型的內容量須受控。批次依文件長度及上下文餘額調整，不預設固定文件數就一定適合。
4.6 使用者尚未提出零遺漏保證、固定主題數、特定資料庫、圖譜、向量模型或框架需求；不要自行加為必要條件。

5 候選方案與選擇理由
5.1 搜尋索引：優先候選為 QMD。它整合 Markdown 分段、關鍵字搜尋、語意搜尋、混合排序、重排序、CLI／MCP、原文定位與增量更新。價值是讓代理按需取得候選資料，減少反覆把大量原文送入上下文。適合日常查找與具體問題追問。
5.1.1 邊界：搜尋排序與候選數會限制模型實際看到的內容；回傳全部搜尋匹配項，也不能證明找齊語意相關資料。QMD 不等於全庫盤點器。
5.1.2 避免重複：若採用 QMD，起步時不要另外重做同等的分段、搜尋、重排序、原文定位與更新機制。
5.1.3 QMD 的 context 是提供給搜尋結果的集合或路徑描述，不是自動產生的逐篇摘要；metadata 也不代表工具會自動理解並產生主題標籤。
5.1.4 成本與未知：初次索引、模型下載、向量建立、查詢等待與更新都要資源；資料語言與硬體未確認，不能宣稱它在此資料庫必然表現良好。若資料以中文為主，須特別驗證嵌入模型及詞彙搜尋表現。
5.1.5 來源：[QMD 官方專案與文件](https://github.com/tobi/qmd)。
5.2 全面盤點工作流程：將「完整來源清單＋逐批處理＋逐來源成果＋持久進度＋一致處理規則」視為一個組合。價值是可核對範圍、可接續、可重跑失敗項目，也能用已保存的成果重新歸納。適合要求涵蓋指定全集的整理。
5.2.1 最小來源清單可記錄來源識別、路徑、段落範圍、來源版本或修改時間、處理狀態與成果位置。成果保留主張或資訊、適用條件、差異及原文位置；具體欄位依任務設定，不先強制萃取所有可能類型。
5.2.2 三者不可互相取代：清單提供處理分母，成果保存內容，進度讓工作可接續。提示詞負責統一操作規則，不能單獨充當上述資料。
5.2.3 成本是需要處理指定範圍內的全部內容，以及保存、檢查與更新成果；不應讓每次簡單查找都先跑全庫。
5.2.4 初期可用代理原生讀寫檔案能力保存普通清單與成果，不必先引入 LangGraph。若日後需要穩定自動排程、重試與跨程序恢復，再評估框架。
5.2.5 這是依使用者需求提出的架構建議，不是已完成的實作。外部筆記與分階段讀取的依據：[Anthropic 上下文工程](https://www.anthropic.com/research/effective-context-engineering-for-ai-agents)；框架能力參考：[LangGraph 持久化](https://docs.langchain.com/oss/python/langgraph/persistence)。
5.3 按需主題目錄與分層摘要：保存已整理過的主題、簡短說明、子主題與來源連結。價值是降低反覆探索同一批內容的成本，讓代理從概覽逐步深入。適合經常重訪的主題及跨文件歸納。
5.3.1 起步可以使用現成標題與檔案路徑，不必先替所有文件產生摘要。優先累積實際任務產生、可回查的主題入口。
5.3.2 成本是摘要生成、來源改動後更新，以及摘要本身可能漏掉細節。未知未來問題不能靠一份固定摘要完整保留。
5.3.3 目前列為後加選項；若反覆出現探索與歸納成本，再驗證其額外價值。
5.4 GraphRAG：先建立實體與關係、社群層級及主題報告，再以全域搜尋整合跨文件內容。價值是對整體資料庫的主題問題提供結構化入口，比單純尋找相似片段更對應宏觀問題。
5.4.1 它本身已包含一種分層主題報告。若選用它，先確認哪些摘要功能已涵蓋，避免另外建一套相同用途的系統。
5.4.2 成本包括抽取、索引、報告生成與更新。全域搜尋仍會對中間內容評分及篩選，不能當作零遺漏的逐文件盤點。FastGraphRAG 與標準流程也有成本及圖品質取捨。
5.4.3 適合反覆提出全庫主題問題，且輕量目錄不足時評估；目前延後，不能直接認定永久無用。
5.4.4 來源：[全域搜尋](https://microsoft.github.io/graphrag/query/global_search/)、[索引方式與成本取捨](https://microsoft.github.io/graphrag/index/methods/)。
5.5 RAPTOR：將文字片段遞迴分群、摘要，形成多層摘要樹，可在不同抽象層取得內容。價值是同時提供原文細節與較高層概覽，適合評估多層次問答需求。
5.5.1 它與 GraphRAG 的圖社群結構不同，但都增加預建概覽的成本。初期不建議兩者同時導入；應先確認輕量方案的缺口，再選適合的候選試用。
5.5.2 目前研究結果不能直接推論為此上萬份文件資料庫的實際效益或完整性保證。
5.5.3 來源：[RAPTOR 原論文](https://arxiv.org/abs/2401.18059)、[作者實作](https://github.com/parthsarthi03/raptor)。
5.6 操作提示詞：應嵌入各工作流程，明定來源查證、處理範圍、成果格式與接續方式。價值是減少操作漂移；單獨要求「不要遺漏」「完整閱讀」不會自動形成索引、進度或覆蓋證據。

6 堆疊與採用順序
6.1 日常模式：搜尋索引 → 多種措辭找候選 → 回讀原文 → 帶來源回答。
6.2 全面模式：明確範圍與來源清單 → 逐批處理原文 → 保存來源成果與進度 → 跨批整理 → 核對未處理與失敗範圍。不能只讓搜尋命中的候選文件充當全集。
6.3 可共用部分是來源識別、原文定位、可重用成果與查證規則。搜尋索引幫助探索與追問；全面模式的清單另負責核對遍歷範圍。
6.4 按需主題目錄可疊在前述成果上；若反覆使用仍不足，再比較分層摘要、GraphRAG 或 RAPTOR。這些不是目前必須全部建好的前置工程。
6.5 使用者尚未批准具體工具選型。QMD 是優先試用候選，並非已驗證的最終答案。

7 mald 篩選紀錄
7.1 橫軸採新增建置與維護負擔；縱軸採淨效用。原則上用節省的查找與複查工時，扣除建置、更新、維護及費用折算工時；同時確認資料查找與整理品質未惡化。
7.2 目前沒有實測工時、費用折算標準、品質評估，也沒有證據支持候選淨效用呈常態分布，因此不填造假的淨效用、峰值百分比或分區。未量測候選列待定，與「優先試用」的建議順序分開。
7.3 QMD＋原文回查：淨效用未測，相對峰值未知，待定但優先試用。拿掉後少了可重用的搜尋入口與明確查證流程。
7.4 全面盤點組合：淨效用未測，相對峰值未知，待定，全面整理時試用。拿掉後無法核對處理範圍，也難以接續。
7.5 按需主題目錄與摘要：淨效用未測，相對峰值未知，待定、後加。拿掉後重訪同一主題時較可能重做探索。
7.6 GraphRAG／RAPTOR：淨效用未測，相對峰值未知，待定、延後。拿掉後少了預建的跨文件主題結構，但不妨礙先使用基本查找與全面盤點流程。
7.7 在 QMD 之外額外重做完全同等的既有功能：不增加功能、另增成本，相對峰值無法計算，依歸併規則捨棄。刪除額外副本後，該能力仍由 QMD 提供。若額外實作有不同且可驗證的能力，須重新評估，不能套用此結論。

8 提示詞範本
8.1 日常查找：「針對我的問題，以不同措辭搜尋候選資料，回讀原文後回答。每項結論附來源位置與支持內容，保留不同條件及矛盾。說明搜尋範圍，將結果稱為目前找到的候選資料；未做全面盤點時，不宣稱涵蓋全集。」
8.2 全面整理：「先固定指定資料範圍與處理目標，建立完整來源清單。依文件長度逐批處理，每份成果保留來源位置、重要觀點、條件與差異。保存完成、失敗與未處理狀態，以及下一批位置。長文未讀完不得標整份完成。先保存個別成果，再跨批歸納；輸出太長時分批保存，不自行縮成固定少數項目。」
8.3 接續工作：「先讀任務目標、來源清單與進度檔，核對既有成果及未完成範圍，從未完成部分接續。不要只依對話摘要推測哪些來源已處理。」
8.4 來源建議先取得支持原文再作答：[Anthropic 長上下文提示建議](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices#long-context-prompting)。以上範本尚未對使用者資料庫實測。

9 接手時仍需確認的資訊
9.1 實際 CLI 與模型、可使用的檔案工具及 MCP 能力。
9.2 文件語言、總字量、長度分布、目錄結構、內容類型，以及是否已有可靠標題或標籤。
9.3 文件新增、修改與刪除頻率；衍生成果的存放位置及更新方式。
9.4 快速查找與全面整理的實際比例、代表性問題、可接受的等待時間、前置費用與人工複查量。
9.5 可用硬體與是否希望全程本機；不要從上下文限制直接推論硬體不足，也不要假定需要特定 GPU。

10 接手後的最小驗證與執行邊界
10.1 若使用者要求繼續落地，先以代表性小範圍與問題比較原本 CLI 查找和候選方案，觀察相關資料漏失、引用準確性、歸納差異、回答耗時、上下文量、建置更新工時與實際費用。沒有改善就不擴充。
10.2 全面整理另檢查來源清單與各狀態是否對得上、長文段落是否完整納入、成果能否回到原文，以及中斷後是否能按進度接續；不能只看完成百分比。
10.3 本次授權是編寫交接文件，不包含安裝、全庫處理或執行腳本。後續工作須遵守使用者既有規約：執行腳本前取得允許，未獲允許不執行 git，不主動讀取未指定文件、隱藏路徑或 `.deprecated/`。
10.4 當前未定案的是具體工具選型、成本與效果；既有結論是先採最小架構，將搜尋與全面盤點分成兩種互補操作模式，再依實際缺口增加摘要或圖譜。
