1. 多時區數據對齊漏洞（Multi-Timeframe Leak）
在代碼中同時引用不同時間週期的數據（例如：在 15 分鐘 K 線策略中，引用日線級別的指標）時，極易在代碼底層引入隱性時間洩漏。

代碼陷阱：
在 15 分鐘線的代碼中寫入 daily_close = request.security(sym, "D", close)。

邏輯失效：
回測系統在計算早上 09:15 的 15 分鐘 K 線時，該代碼返回的「日收盤價（daily_close）」實際上是當天下午 13:30 收盤時的價格。此代碼在回測中運行無誤，但本質上是讓早上的決策讀取了下午的結果。

正確寫法：
代碼必須強制設定對齊偏移量（如使用 close[1]），確保讀取的日線數據是「昨日已收盤」的數據。

2. 限價單「觸及即成交」假象（Limit Order Fill Fallacy）
多數回測引擎在處理限價單（Limit Order）時，採用極度簡化的成交邏輯。

代碼陷阱：
回測代碼邏輯為 if (Low <= LimitPrice) fill_order();。

邏輯失效：
在實際市場中，當價格「觸及」你的限價時，你必須在交易所的訂單簿（Order Book）中排隊。如果該價格僅有極少數的成交量即反彈，你的訂單根本不會成交。

財務損耗：
此漏洞會使回測虛增大量獲利。例如回測顯示獲利新臺幣 150,000 元，實盤因排隊失敗未成交，實際獲利為 0 元。

3. 浮點數精度與等值比對失效（Floating-Point Precision Mismatch）
價格與指標在計算機底層是以二進位浮點數儲存，這會導致看似簡單的數值比對在代碼執行時永久失效。

代碼陷阱：
if (CurrentPrice == TargetPrice) ClosePosition();（例如比對價格是否剛好等於 105.15）。

邏輯失效：
在計算機中，105.15 可能被儲存為 105.150000000000005。當實盤價格傳入為 105.15 時，兩者在二進位層面不相等，導致出場代碼永遠無法觸發，小虧損最終放大為巨額穿價。

正確寫法：
不使用 ==，必須改用小於等於、大於等於，或定義極小值差距：if (abs(CurrentPrice - TargetPrice) < 0.0001)。

4. 異步狀態機同步失效（Asynchronous State Desynchronization）
在實盤代碼中，下單指令發送與帳戶狀態更新存在物理上的時間差。

代碼陷阱：

Python
SendOrder(Buy, MarketPrice)
if GetPosition() == 0:
    SendOrder(Buy, MarketPrice) # 避免漏單的補單邏輯
邏輯失效：
實盤執行時，API 發送訂單到交易所確認成交需要時間（中位數延遲約 50 毫秒）。在收到成交回報前，代碼已經執行到下一行，此時 GetPosition() 依舊返回 0。代碼判定漏單，再次發送買進指令。

財務損耗：
策略在瞬間重複下單，導致持倉翻倍，直接面臨未預期的資金暴露與新臺幣數萬元的超額虧損。
